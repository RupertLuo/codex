# 增量请求与图片缓存设计

本文只记录当前代码已经实现的请求契约，不把某个 Provider 的缓存命中承诺扩大成 Codex 通用保证。

## 一、目标

对宿主声明支持 HTTP 增量请求的 model：

- 连续请求只在输入前缀相同时发送 suffix。
- `previous_response_id` 只引用当前 session 保存的响应。
- provider 不认识旧 response 时自动回退 full request。
- 如果 provider 要求工具输出图片成为相邻的 user message，Core 在迁移后保存 typed baseline，并在下一次比较时使用同一变换。

## 二、代码路径

`ModelRuntimePolicy` 位于 `codex-rs/core/src/client.rs`，目前控制：

- `supports_http_incremental_requests`
- `relocates_tool_output_images`
- `max_request_body_bytes`
- `supports_parallel_tool_calls`（可选覆盖并行工具调用能力）

发送流程在 `ModelClientSession` 中执行：

1. 按 model policy 对 request input 做图片迁移。
2. 在迁移完成后 clone 完整 request，作为下一次比较的 baseline。
3. 取 session-scoped 的上一个 request 和 response。
4. 只有非 input request fields 相容且前缀匹配时，发送 suffix 并设置 `previous_response_id`。
5. 成功响应后保存完整 baseline；增量请求遇到明确的 unknown previous response，清理本轮增量状态并重发 full request。

Core baseline 不是最终编码的 wire JSON。Runtime 在随后执行 Provider JSON 归一化、图片重编码及体积检查；
这些变换必须对同一历史前缀保持确定性，图片迁移须幂等。不能在两轮之间对相同前缀做不稳定重排或重编码。

## 三、图片迁移契约

对于 `FunctionCallOutputContentItem::InputImage`：

- 从 function output 中移除图片内容。
- 保留其余 output content；图片-only output 仍是空 array，不是空字符串。
- 在 function output 后插入相邻的 user `message`，图片保持原顺序。
- 迁移在同一个 request 内完成，重复进入时不应再制造重复图片 message。

该逻辑解决的是本地 request shape 和 incremental baseline 的一致性，不保证 Qwen 或其他 provider 的多模态 cache 永远命中。

## 四、验证

以下是源码测试入口，本次治理未执行测试。`incremental_http.rs` 目前有两个 integration case，直接证明文本跨 turn 增量与失效回退；不能据此宣称图片组合与 byte-budget 全矩阵已覆盖。

主要证据：

- `codex-rs/core/tests/suite/incremental_http.rs`：HTTP suffix、baseline、full fallback 和 model policy。
- `codex-rs/core/tests/suite/client.rs`：`previous_response_id` 的请求行为。
- `codex-rs/core/tests/suite/client_websockets.rs`：上游 WebSocket incremental 行为不能因 HTTP patch 被破坏。

验证时至少检查：

```text
普通文本 output 不丢失
图片-only output 保持 []
多张图片保持顺序
第二个请求复用 previous_response_id 且只发送 suffix
previous response 不存在时恢复 full request
```

不要为一次 provider live probe 重置 client session；优先使用 deterministic request-shape test 证明本地契约。

## 五、跨层回退与继续增量

Runtime `crates/catalyst-codex/tests/qwen_incremental_fallback.rs::synthetic_policy_to_core_fallback_matrix`
包含 `image_baseline_404` 场景：合成工具图片历史 → 正常请求 → 增量失效 → 完整重发 → 以恢复 ID 继续增量。
它使用生产 catalog policy、Core ModelClient、CatalystTransport 与 QwenPolicy，在内存 upstream 捕获最终请求；
断言图片-only 空数组、混合文字保留、多图片顺序、完整重发一致，以及恢复后的 suffix 不重复旧图片。

该场景不执行真实工具、不访问图片 URL、不覆盖大图重编码或未 Completed 流恢复。OpenAI 的 HTTP 增量策略保持关闭；
后续优化先验证 Runtime policy 是否足够，不因优化意图直接扩展 Core。
