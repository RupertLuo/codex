# Catalyst Codex 上游同步手册

目标不是把旧 fork 整体搬到新 release，而是从新的官方 Codex 开始，只重新接入仍有产品价值、且没有被上游替代的
Runtime 能力。

## 一、准备和基线

```bash
git fetch upstream --tags --prune
git show <upstream-tag-or-commit>^{commit} --no-patch --decorate
git status --short --branch
```

当前升级候选基线（验证范围见 [升级记录](06-0.153.4升级验证.md)）：

```text
rust-v0.153.4
```

同步前必须先提交或明确记录当前主线的 clean revision。不要以其他版本的差异统计替代当前代码审查。

## 二、盘点 fork delta

```bash
git diff --stat <upstream-tag-or-commit>..HEAD
git diff --name-status <upstream-tag-or-commit>..HEAD
git log --oneline --left-right <upstream-tag-or-commit>...HEAD
```

逐项归类：

- `upstream equivalent`：上游已有等价能力，删除本地 duplicate。
- `retained patch`：仍由宿主或产品契约需要。
- `adaptation`：保留行为，但按新 API/lifecycle 重新接入。
- `test/generated`：测试、schema、snapshot、lock 等随实现更新。
- `infrastructure`：只服务于构建、发布或同步流程。

## 三、冲突解决原则

优先顺序：

1. 先保留上游安全、协议、持久化和 session 生命周期变化。
2. 再检查能否通过 `ThreadManagerRuntimeOptions`、App Server overrides、provider 或 extension 接回能力。
3. 只将最小行为接入 boundary，不恢复整个旧文件或旧调用链。
4. 为每个能力确定 focused test，集中实施后统一验证，并更新 `docs-cata/01-Patch地图.md` 的证据。

对 `core`、`protocol`、`state`、`security`、`app-server` 文件禁止用 blanket `ours` 或 `theirs`。

重点复核：

```text
codex-rs/core/src/thread_manager.rs
codex-rs/core/src/client.rs
codex-rs/core/src/session/
codex-rs/app-server/src/lib.rs
codex-rs/app-server/src/catalyst/rpc_extension.rs
codex-rs/ext/skills/src/sources.rs
codex-rs/thread-store/src/live_thread.rs
codex-rs/tui/src/catalyst/model_runtime.rs
codex-rs/windows-sandbox-rs/src/desktop.rs
```

## 四、验证顺序

先从 Patch 地图选出受影响能力及测试，核对根 `justfile` 的参数转发。Fork 使用 nextest；Runtime 使用其自己的 workspace 测试命令。两者不能互相代替。

以下是精确测试示例（在 fork 根运行；执行前核对当前用例仍存在）：

```bash
just test -p codex-core --test all -E 'test(=suite::incremental_http::host_policy_resends_full_history_when_previous_response_expires)'
```

只修改文档时检查本地链接、原版 AGENTS 身份和 `git diff --check`。Rust 代码修改后按原版规则执行格式检查；协议、配置或 UI 变化分别生成 schema 或审查 snapshot；依赖变化还需维护 Bazel lock。不要为了文档治理启动全量格式化或构建。

能力实现集中完成并冻结 findings 后，由集成负责人汇总一次最低充分验证；只有变更共享不变量或证据不足时才扩大到 crate。全量测试、真实平台及 packaged 验证按本次授权和升级范围选择，不是每次同步的默认前置步骤。

### 宿主联合验收

嵌入 Codex 的 Runtime 与 Workbench 共同消费升级结果。同步验收由同一集成负责人汇总，按实际变化选择
场景，复用同一源码快照已有的证据；不要求每次同步全量测试或改动三个仓库。

| 验收边界 | 最低充分证据与入口 |
| --- | --- |
| 源码与装配身份 | 记录 Workbench、Runtime、Codex 的 revision 与未提交差异；指定本次使用的装配路径，另记录产物 identity。Runtime `crates/catalyst-app-server/src/rpc/runtime.rs` 产出 handshake，Workbench `crates/codex-runtime-client/src/session.rs` 校验身份。不同装配路径的 lock 不为追齐源码 HEAD 而改写。 |
| 宿主能力接线 | 按[Patch 地图](01-Patch地图.md)的五类注入与消费路由，验证本次受影响能力；模型或工具转换需覆盖 Runtime 的实际 policy/output 到 Codex 的消费，不能只验两端各自的 mock。 |
| DTO 与事件 | 对本次改变的 request、response、server request 或 notification，沿 Runtime schema/producer 到 Workbench decoder/fold 验证字段与语义。Runtime `crates/catalyst-app-server/src/schema.rs` 的 schemaDigest 是身份摘要，不包含完整 DTO 和事件定义；握手通过不能代替兼容验收。 |
| 历史读取与继续 | 使用明确 N-1/N 组合和合成或脱敏历史 fixture，分别验证 read、宿主首窗/resume、分页及恢复后新 turn；受影响的模型、工具名、权限和停止行为需保留。Workbench 首窗可调用 resume，不能把 UI 打开历史视为纯 read。 |
| 数据回退 | 区分 N 尚未写入与写入后；写入后需证明旧 reader 可解释，或按 Workbench `docs/400-contracts/430-customer-data-and-upgrades.md` 恢复升级前完整恢复单位。不得把更换旧二进制当作数据回退证明。 |

版本支持窗口和 consumer-first 规则沿用 Workbench `docs/400-contracts/480-versioning-and-compatibility.md`。
没有选定升级组合时，记录尚未取得 N-1/N 资格，不以当前版本单测代替。每项结果绑定源码或产物身份，并注明
未覆盖平台；本地源码验证不等于真实平台、安装包或发布资格。

### 当前补丁的精确验收选择

下表是按受影响边界选用的最小入口，不是每次升级必须全部执行的测试清单。函数全名和所在 target 以当次源码为准；本轮执行结果见[架构治理](05-宿主消费与架构治理.md)第 8–11 节。

| 上游变更触及 | Fork / Runtime 验收入口 | 仍需单独决定的资格 |
| --- | --- | --- |
| 工具规划和搜索替代 | fork `core/src/tools/spec_plan_tests.rs` 的 capability、gate、collision 用例；Runtime search executor capability 用例 | 历史工具名保持；新 feature/mode 组合按变化补充 |
| 增量、图片或请求状态 | Runtime `qwen_incremental_fallback` 的 `synthetic_policy_to_core_fallback_matrix`；按变化选择 Provider body/image tests | typed baseline 与最终 wire 分层；合成历史不等于真实大图执行 |
| RPC registry / initialize 分发 | fork `rpc_extension_tests.rs` 两例和 `message_processor_rpc_tests.rs` 一例 | 改动 queue/cancel/native gateway 时补对应 lifecycle；真实 transport 认证另验 |
| process MCP 配置 | fork `cli_tests.rs` 一例和 `config_manager_tests.rs` 两例 | 实际子进程启动/替换及相对路径按改动另验 |
| Runtime 入口接线 | Runtime `runtime_composition::image_capable_model_plans_product_tools_without_hosted_duplicates`；binary `tests::catalyst_tui_assembly_preserves_runtime_extensions_and_optional_catalog`（需 `test-support`） | Browser 条件组合、TUI 最终 wire 和界面交互不由装配单测代替 |

本轮治理只修改 fork 与 Runtime。Workbench 在未来升级中是否需要联动取决于公开 DTO、事件、历史或发布契约是否变化；不能将本轮无需修改视为永久无影响保证。

## 五、晋级条件

- upstream ancestry 可由 tag/commit 直接验证。
- 每个保留能力都有代码 boundary、调用方和 focused test。
- 上游已替代的 duplicate 已删除或明确标记为 superseded。
- schema、lock、snapshot、格式和 `git diff --check` 干净。
- 涉及宿主的变化已完成上述受影响边界的联合验收；升级组合、支持窗口和未覆盖资格明确。
- 文档只保留可复用规则和当前有效入口，不保留机器 handoff 或过期过程日志。
