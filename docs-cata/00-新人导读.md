# Catalyst Codex 新人导读

本仓库不是从头实现一个新的 Agent，而是在 OpenAI Codex 上保留少量宿主 Runtime 所需能力。阅读时先区分上游执行引擎、fork 接入接口与宿主产品实现。

## 一、项目关系

```text
OpenAI Codex
    |
    | upstream tag rust-v0.149.0
    v
Catalyst Codex Fork
    |
    | host/runtime injection
    v
Catalyst Runtime or embedding application
```

当前仓库包含 `codex-rs/` Rust workspace。宿主可以通过公开的 runtime options、transport、skill provider、
RPC extension、title generator 和 TUI model runtime 接入能力，而不是复制 Codex session 或重写 App Server。

## 二、最重要的概念

| 概念 | 含义 |
| --- | --- |
| 官方基线 | 本主线当前使用的 `rust-v0.149.0` |
| fork delta | 当前 HEAD 相对该基线的全部代码、测试、依赖和生成物变化 |
| Catalyst patch | fork delta 中仍属于 Catalyst 产品契约的最小部分 |
| 上游适配 | 为适应上游 API、生命周期或类型而产生的必要变化 |
| Runtime boundary | 宿主向 Codex 注入能力的显式接口，而不是隐式全局状态 |

正确关系是：

```text
fork delta = Catalyst patch + 上游适配 + 测试/生成物 + 工程基础设施
```

## 三、源码如何进入运行时

1. 宿主构造 `ThreadManagerRuntimeOptions`，按需注入 HTTP transport、静态 model catalog、强制基础指令、
   runtime extension、skill provider、title generator 和 model runtime policy。
2. App Server 通过 `AppServerProcessOverrides` 将进程级覆盖传给 Thread Manager，并注册 `AppServerRpcExtension`。
3. Thread Manager 在创建 session 时把这些能力传到上游的 client、session、thread store 和 extensions boundary。
4. TUI 通过 `TuiModelRuntime` 处理模型可用性、credential 保存/重验证/删除和 provider onboarding；敏感输入会
   脱敏 Debug，并在释放时 zeroize。
5. 这些 Rust 源码参与 Cargo/Bazel 编译，进入最终二进制；源码文件本身不会因为 path dependency 自动成为运行时配置。

## 四、从哪里开始看

- 先读 `AGENTS.md` 和 `AGENTS.origin.md`，明确本地规则与官方规则的关系。
- 再读 `docs-cata/01-Patch地图.md`，按能力选择代码入口。
- 需要判断一个文件是否真的属于 patch 时，运行 `git diff --name-status rust-v0.149.0..HEAD`，再追提交和测试。
- 修改上游核心逻辑前，先确认能否通过已有 Runtime boundary 接入；修改后必须留下 focused test。

## 五、判断口诀

```text
先定官方基线，再看 fork delta。
先找 Runtime boundary，再决定是否改 core。
保留上游安全、协议、持久化和生命周期不变量。
代码是运行时输入，patch 文件不是运行时机制。
能由上游提供的能力，不在 fork 中重复实现。
```
